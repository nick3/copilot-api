# Admin UI Responses Tool Search Visibility

> Spec generated by `/office-hours`, then locked by `/plan-eng-review`.
> Branch: `feature/mcp-streamable-http`
> Status: DRAFT, engineering-reviewed

## Problem

When Copilot sends a Responses API request that uses `tool_search`, the proxy already bridges that call into Claude-facing tool-search behavior, but the Admin UI request log does not show whether the upstream model actually used tool search or how many deferred tools were involved.

That makes a real production/debug question hard to answer:

- Did the upstream Responses API call `tool_search` at all?
- How many tool names did it request?
- How many deferred tools were available in the forwarded request?
- How many deferred tools were ultimately forwarded into the Anthropic request?
- Did parsing fail, or is a displayed zero genuinely a known zero?

Today an operator has to infer this by reading payloads and stream events manually. That is slow, error-prone, and easy to misread.

## Goal

Persist and display explicit tool-search telemetry for Responses requests in the Admin UI.

A request should show:

1. `called`: whether the upstream Responses output contained at least one `tool_search_call`.
2. `requested_count`: the count of unique deferred tool names requested by all completed `tool_search_call` items, when known.
3. `requested_parse_status`: whether the requested names were parsed cleanly, partially, or not at all.
4. `forwarded_count`: how many deferred tools the bridge selected and forwarded to Anthropic.
5. `available_count`: how many deferred tools were available in the final Responses payload sent upstream.

The important product behavior: the Admin UI must tell the difference between “not called,” “called but parser could not know,” and “called with zero known names.”

## What already exists

- `src/lib/tool-search.ts` already owns deferred-tool normalization and selection.
  - `listDeferredToolNames()` returns available deferred tool names.
  - `parseDeferredToolNames()` accepts `names`, `query`, or `paths` bridge argument shapes.
  - `normalizeToolSearchBridgeArguments()` and `formatToolSearchBridgeArguments()` already define the bridge argument contract.
  - `selectDeferredToolsByNames()` already computes the forwarded tool subset.
- `src/routes/messages/responses-translation.ts` already maps non-streaming Responses `tool_search_call` output back into Anthropic `tool_use` content.
- `src/routes/messages/responses-stream-translation.ts` already tracks stream output items and receives complete `tool_search_call` items at `response.output_item.done`.
- `src/routes/messages/handler.ts` already has a single request-history insertion path per request outcome through `insertRequestLog()`.
- `src/lib/admin-db.ts` already has a versioned SQLite migration pattern through `PRAGMA user_version`.
- `src/lib/request-history.ts` already defines request-history insert and read types.
- `admin-ui/src/lib/admin-api.ts` already normalizes SQLite wire values into UI-friendly request objects.
- `admin-ui/src/pages/requests-page.tsx` already renders compact request list metadata.
- `admin-ui/src/pages/request-detail-page.tsx` already has detail-page sections where routing/debug metadata can be added.

The plan reuses these paths. It does not build a parallel request log, a second payload parser, or a separate Admin API endpoint.

## Decision Summary

### 1. Persist telemetry in request history

Add nullable columns in the next `request_log` migration. The current branch appears to be at user version 13, so the implementation is expected to add v14, but the implementer must confirm the current `PRAGMA user_version` before writing the migration.

Planned columns:

```sql
responses_tool_search_called INTEGER NULL,
responses_tool_search_requested_count INTEGER NULL,
responses_tool_search_requested_parse_status TEXT NULL,
responses_tool_search_forwarded_count INTEGER NULL,
responses_tool_search_available_count INTEGER NULL
```

Wire semantics:

```text
NULL  = unknown / not applicable / incomplete telemetry
0/1   = known boolean for called
number = known count
requested_parse_status = not_called | ok | partial_unknown | unparseable
```

Do not write `false` or `0` when the request failed before the relevant signal was observed. Silent certainty is worse than missing telemetry.

### 2. Use one telemetry object per request

Add a single telemetry object owned by a small observer/helper. The translator and stream translator should not scatter ad-hoc fields through the handler.

```ts
type ResponsesToolSearchRequestedParseStatus =
  | "not_called"
  | "ok"
  | "partial_unknown"
  | "unparseable"

type ResponsesToolSearchTelemetry = {
  availableCount: number | null
  called: boolean | null
  requestedCount: number | null
  forwardedCount: number | null
  requestedParseStatus: ResponsesToolSearchRequestedParseStatus | null
  requestedKnownNames: Set<string>
  outputComplete: boolean
}
```

Ownership rule:

```text
handler
  ├── creates one observer/helper for the request
  ├── passes observer to non-stream / stream translation paths
  ├── finalizes observer once request outcome is known
  └── writes finalized values through insertRequestLog()

translation paths
  ├── report available deferred tools from final Responses payload
  ├── report complete tool_search_call items when observed
  └── report forwarded deferred tools after selection
```

Only the observer/helper mutates telemetry. The handler finalizes and logs it. This keeps lifecycle state in one place.

### 3. Source available and forwarded counts from the final payload

`available_count` and `forwarded_count` must be derived from the final Responses payload that is actually sent upstream, not from raw Anthropic request input and not from pre-normalized handler guesses.

Reason: payload shaping happens inside translation. Counting earlier can drift when normalization, filtering, or future payload transforms change.

Expected source of truth:

```text
Anthropic request
  ↓ translateAnthropicMessagesToResponsesPayload()
final Responses payload sent upstream
  ├── count deferred tools available to upstream tool_search
  └── later tool_search output selects forwarded deferred tools
```

### 4. Share requested-name analysis through `src/lib/tool-search.ts`

Move the “extract requested names plus parse status” logic into a shared helper in `src/lib/tool-search.ts` so non-streaming and streaming paths use the same parser.

Planned helper shape:

```ts
type DeferredToolNameAnalysis = {
  knownNames: string[]
  status: "ok" | "partial_unknown" | "unparseable"
}

function analyzeDeferredToolNamesFromToolSearchArguments(
  rawArguments: unknown,
): DeferredToolNameAnalysis
```

Rules:

- Object arguments with a valid `names` array are `ok`.
- Alternate known bridge shapes that the existing parser supports (`query`, `paths`) should map consistently with current behavior.
- Malformed JSON or non-object arguments are `unparseable`.
- Recognized argument containers that contain unknown or partially unusable name data are `partial_unknown`.
- Empty valid arrays are `ok` with count `0`.

### 5. Aggregate multiple `tool_search_call` outputs as a unique union

If a response emits multiple `tool_search_call` items, `requested_count` means the count of unique known requested names across the full response, not the sum of each call.

Status merge rule:

```text
if no tool_search_call observed       => not_called
else if any call is unparseable       => unparseable
else if any call is partial_unknown   => partial_unknown
else                                  => ok
```

This avoids double-counting repeated requests while still surfacing malformed calls.

`requested_count <= available_count` is not a hard invariant. It is normal to expect it in clean cases, but protocol drift, stale upstream names, or cross-call behavior can violate it. The UI should show the known requested count plus `requested_parse_status`; tests should not enforce a misleading inequality.

### 6. Streaming source of truth

For streaming Responses output:

```text
response.output_item.added
  └── may mark tool_search as called if item.type is tool_search_call

response.output_item.done
  └── only source used for requested names and parse status
```

Do not parse partial argument deltas for `requested_count`. Partial deltas are allowed to be incomplete and are too easy to misaggregate. `response.output_item.done` contains the complete item and is the right lifecycle boundary for counts.

### 7. Admin API normalization stays in the UI client

Keep Admin API wire rows SQLite-shaped. Add raw nullable columns to the wire type, then normalize in `admin-ui/src/lib/admin-api.ts`.

That matches the existing `is_subagent` pattern and avoids creating a second backend DTO layer for one feature.

Planned normalized UI shape:

```ts
type ToolSearchTelemetryView = {
  called: boolean | null
  requestedCount: number | null
  requestedParseStatus:
    | "not_called"
    | "ok"
    | "partial_unknown"
    | "unparseable"
    | null
  forwardedCount: number | null
  availableCount: number | null
}
```

### 8. Request list display uses an existing metadata cell

Do not add a standalone request-list column. The list already has limited horizontal budget.

Add a compact badge inside the existing path/model metadata area:

```text
Tool search · 3
Tool search · ?
Tool search · partial
```

Display rule:

- Show no badge when `called !== true`.
- Show the known requested count when `called === true` and `requested_count` is known.
- Show `?` or `partial` when called but parsing was not clean.
- Keep the detail page as the full source of truth.

### 9. Detail page display is explicit

The request detail page should show all five values with clear unknown states:

```text
Tool Search
  Called: yes / no / unknown
  Requested tools: 3 / unknown / unparseable / partial
  Parse status: ok / partial_unknown / unparseable / not_called / unknown
  Forwarded tools: 3 / unknown
  Available deferred tools: 9 / unknown
```

Use plain labels. Avoid clever abbreviations. Operators should not need to remember what each count means.

## Failure Semantics

Do not collapse unknown into false/zero.

```text
Scenario                                      called     requested_count     parse_status
------------------------------------------------------------------------------------------------
Non-Responses request                         NULL       NULL                NULL
Responses request, no tool_search observed    0          NULL or 0*           not_called
Tool search called with valid names           1          N                   ok
Tool search called with empty valid names      1          0                   ok
Tool search called, malformed arguments        1          NULL                unparseable
Tool search called, partial unknown shape      1          known union or NULL  partial_unknown
Request errors before output observed          NULL       NULL                NULL
Stream disconnects before output done          1 or NULL  NULL                NULL or unparseable**
```

`*` Choose one representation and test it. Recommendation: `requested_count = NULL` with `parse_status = not_called`, because no request count exists when no call exists.

`**` If `output_item.added` proves a tool-search call started but `done` never arrives, store `called = 1`, `requested_count = NULL`, and a non-`ok` status. Prefer `unparseable` only if a complete malformed item was observed; otherwise keep status unknown/null so the UI does not invent certainty.

## Failure Modes

| Codepath | Production failure | Test coverage required | Error handling / user result |
|---|---|---|---|
| Final payload counting | Future translation changes filter deferred tools after early counting | Integration test counts from final payload | User sees accurate available/forwarded values |
| Requested analyzer | Upstream sends malformed `arguments` string | Parser unit test and handler test | User sees `unparseable`, not `0` |
| Multi-call aggregation | Same deferred name requested by multiple calls | Unit/integration test for unique union | User sees stable unique count |
| Stream lifecycle | Stream disconnects after `output_item.added` before `done` | Stream handler test | User sees called with unknown count, not false/0 |
| Request error path | Responses request fails before output is observed | Handler failure test | User sees unknown telemetry rather than misleading certainty |
| Migration | Existing DB upgrades without new nullable columns | Migration upgrade test | Admin UI reads rows without runtime failure |
| Admin API normalize | SQLite `NULL` is accidentally coerced to `0` | UI normalization test | User sees unknown labels, not fake zero |
| Request list layout | Extra column compresses useful request data | UI render test/snapshot | User sees compact badge in existing cell |

Critical gaps before implementation: none remain in the plan once the tests above are included. The highest-risk test is the handler failure path because it prevents silent false/zero writes.

## NOT in scope

- New standalone request-list column: deferred to preserve list readability; use an existing metadata cell badge instead.
- A new Admin API DTO layer: deferred because `admin-api.ts` already normalizes SQLite-shaped wire rows consistently.
- Enforcing `requested_count <= available_count`: deferred because it is not a reliable protocol invariant.
- Parsing streaming partial argument deltas: deferred because `output_item.done` is the complete source and avoids partial aggregation bugs.
- Blocking ship on a real upstream sample: deferred because local mocks cover the implementation contract; a replay fixture is tracked as follow-up.
- Product analytics or metrics dashboards: deferred; this is request-history/debug visibility only.
- Reworking the broader Responses translation architecture: deferred; this feature should be a right-sized telemetry addition.
